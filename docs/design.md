# 毛遂 · 方案设计

> 版本：v0.1 · 2026-10-22
>
> 上游文档：[白皮书](whitepaper.md)（v0.4）。本文档不重复论证「为什么做」，只回答「做成什么样」。
> 证据分级沿用白皮书：`FACT` / `SIGNAL` / `HEURISTIC` / `待验证`。

---

## 1. 产品形态

### 1.1 能力包，不是应用

毛遂没有 UI、没有服务端、没有安装器、不发布到任何包管理器。它是一组文件，放进 harness 能读到的位置即可用。

这个选择不是偷懒，是白皮书三条硬承诺的直接后果：不碰凭据、不做托管、不群发。任何一条要落地，最省事的做法都是「别做应用」。

### 1.2 目录结构

```
maosui/
├── README.md
├── docs/
│   ├── whitepaper.md          白皮书：为什么做
│   ├── design.md              本文档：做成什么样
│   └── architecture.md        架构：怎么实现（未开始）
├── skills/
│   └── maosui/SKILL.md        技能入口，供能自动发现技能的 harness 使用
├── workflow/
│   ├── 00-profile.md          建档：简历 → 结构化档案
│   ├── 01-screen.md           筛选：批量 JD → 排序队列
│   └── 02-open.md             开口：圈选岗位 → 第二条消息
├── platforms/
│   └── platform-a.md          适配层：会话机制、约束、（未来的）页面动作序列
├── templates/
│   └── profile.md             结构化档案模板，落到本地 .maosui/profile.md
├── scripts/
│   └── validate-message.py    第二条消息硬校验（可选，见 §3.4）
└── .gitignore                 排除 .maosui/
```

三层对应白皮书 §6.1：`workflow/` 是通用工作流（harness 无关），`platforms/` 是平台适配层（可扩展），`skills/` 是技能入口（harness 相关，但只是薄壳）。

### 1.3 一条关键的分层原则

> **`workflow/` 里的每个文件都必须自包含：原样贴进任何一个纯对话模型，就能跑出正确结果。**

这是 harness 无关性的实现方式——不是靠抽象层适配不同 harness，而是把底座做到最弱 harness 也能用。强 harness 只是**额外**获得自动发现（`skills/`）和硬校验（`scripts/`），不需要维护多套工作流副本。

代价：workflow 文件会比「只给强 harness 用」的写法啰嗦，因为不能假设 agent 知道上下文里有什么。这个代价值得付，否则每支持一个新 harness 就要写一套新流程。

## 2. 用户旅程

### 2.1 先明确一件事：v1 里「操作」不是 agent 的能力

白皮书 §4.1 列了四个动作：提取、操作、匹配、开口。在 v1（Tier 0）下它们的执行者是：

| 动作 | 执行者 |
|---|---|
| 提取 | agent |
| **操作** | **用户手动**——浏览平台、点开岗位、复制 JD、点「立即沟通」、粘贴发送 |
| 匹配 | agent |
| 开口 | agent 生成，**用户手动发送** |

原始需求把「操作」写成 agent 的动作之一。在 Tier 0 下它不是。这不是遗漏，是 §6.3 论证过的选择（人类节奏本身就是产物质量的一部分）。文档必须写清楚，否则使用者会以为毛遂会替他刷岗位。

### 2.2 阶段 A：建档（一次性，约 10 分钟）

1. 使用者把已有简历交给 agent。形态取决于 harness：本地文件路径（档位 A/B）或直接粘贴全文（档位 C）。
2. agent 按 `templates/profile.md` 提取结构化档案。
3. **agent 输出档案，使用者逐项确认或修正后，才落到 `.maosui/profile.md`。**

第 3 步不可省略，理由见 §3.2。

### 2.3 阶段 B：批量筛选

1. 使用者在平台上正常浏览，把值得看的岗位 JD 收集起来，一次交给 agent。**建议一批 5–15 个**——太少省不了事，太多则使用者的圈选决定会变成走过场。`HEURISTIC`
2. agent 逐个对比档案，输出**排序队列**。每个岗位含：匹配档位、对应上的点、对应不上的点、建议。
3. 队列按匹配度排序，但**不按匹配度过滤**——低匹配的岗位也要列出来并说明为什么低，否则使用者无法判断是 agent 筛错了还是岗位真的不合适。

### 2.4 阶段 C：圈选

使用者读队列，明确说出要为哪几个岗位开口（例如「2、5、7」）。

**这一步必须独立存在，不能和阶段 D 合并。** 理由：如果匹配判断和文案同时出现，一份已经写好的、读起来很顺的文案会推着使用者发送——决定就变成「要不要浪费这段文字」，而不是「这岗位值不值得开口」。白皮书把「筛得准」放在「写得像人」前面，这个顺序必须在交互上体现出来，否则定位是空话。

### 2.5 阶段 D：批量生成

agent 只为圈选的岗位生成第二条消息，每条附自检行（见 §3.4）。

### 2.6 阶段 E：逐个发送（agent 不参与）

对每个岗位，使用者：

1. 在平台上点「立即沟通」→ 固定招呼语自动发出（不可控，接受）
2. 复制毛遂生成的第二条消息，粘贴到聊天框，发送

**两个岗位之间不要连续操作。** 招呼语后紧跟第二条是正常的（人类也会这样），但连续对多个岗位秒发会产生机器节奏。具体间隔 `待验证`（白皮书 §9.3 第 6 项），在标定前遵循一条朴素规则：**你自己手动写这些消息会用多久，就花多久。**

### 2.7 阶段 F：回填（可选）

使用者在 `.maosui/log.md` 里记一笔：发了几个、回了几个。agent 不接触平台，看不到回复，这一步只能人工（白皮书 §5.4）。

不强制。强制的记录不会被执行。

## 3. 能力边界

### 3.1 结构化档案的字段

```
## 硬性条件
期望城市 / 期望岗位类型 / 期望薪资区间 / 到岗时间 / 红线（不接受的条件）

## 技能
按「语言 · 框架与库 · 工具与平台 · 领域知识」分组
每项附一句话使用场景，不设熟练度自评

## 项目经历
项目名与时间段 / 我的角色 / 技术栈 / 可量化的结果 / 能对应哪类 JD 要求

## 明确不含
手机号、邮箱、身份证号、住址、照片
```

两个设计决定：

**不设熟练度自评。** 自评不可靠（「精通」的含义因人而异），而 JD 匹配真正依赖的是「有没有用过、用来做过什么」。写使用场景比打星级有用。

**「可量化的结果」是必填项，不是加分项。** 这是整个方案里最重要的一条：**建档质量决定开口质量的天花板。** 一条好的第二条消息形如「你们 JD 里要求 X，我在 Y 项目把 Z 从 A 做到了 B」。如果档案里没有可量化结果，再好的 prompt 也只能产出空话——而空话正是毛遂要消灭的东西。提取阶段遇到简历里没写数字的经历，应当标记为「无量化锚点」，而不是替使用者编一个。

### 3.2 提取动作的红线

agent 不得新增简历中不存在的内容。档案生成后必须由使用者确认才落盘，因为：模型提取时的「合理补全」是伪造经历最常见的入口，而使用者本人是唯一能发现它的人。

这条对应白皮书 §4.2 第 6 项（不伪造经历）。

### 3.3 匹配输出的格式

```
### 岗位 3 · <岗位名> · <公司>

匹配度：高 / 中 / 低
建议：开口 / 可开口 / 不建议

对应上的：
- JD「<原文片段>」→ 我的「<档案里的具体经历>」

对应不上的：
- JD「<原文片段>」→ 我缺 <什么>

判断依据：<一句话>
```

**不给数字分数。** 「匹配度 78 分」暗示了一种并不存在的精度——权重怎么定的、78 和 74 有什么区别，都说不清。三档 + 可核对的理由更有用：使用者能直接看出 agent 是漏读了 JD 还是错判了经历，这满足白皮书 §4.1 里「不同意打分时能看出错在哪」的成功标准。

### 3.4 第二条消息的产出格式

```
### 岗位 3 · 第二条消息

<纯文本正文>

---
自检：字数 NN · 无链接 · 无联系方式 · 未重复招呼语
锚点：引用 JD「<原文片段>」← 对应我的「<经历>」
```

正文遵守白皮书 §6.5 全部规范（不重复招呼语、不提第一条是自动发的、纯文本、不堆砌、结尾给易答问题、80–150 字）。

**关于「纯文本硬校验」，这里要说一句实话。** 白皮书 §5.2 要求该约束在实现层是硬校验而非只写在文档里。但能力包形态下能做到的程度取决于 harness：

| harness 能力 | 校验强度 |
|---|---|
| 能执行代码（档位 A） | `scripts/validate-message.py` 真硬校验，不通过则不输出 |
| 不能执行代码（档位 B/C） | 只有指令自检 + 上面那行可见的自检标记 |

**档位 B/C 下这是软约束**，模型有可能自检通过而实际不合规。缓解手段是把自检结果打印出来让使用者肉眼可查——这不是等价于硬校验，但是在不能跑代码的环境里能做到的最好程度。文档不声称它更强。

### 3.5 毛遂不做的事（v1）

- 不浏览平台、不检索岗位、不读岗位链接（Tier 0 无浏览器能力；`platforms/platform-a.md` 里的页面动作序列留空）
- 不发送任何消息
- 不生成或修改简历（v2 的定向简历才涉及，且受白皮书 §4.2 第 6 条边界约束）
- 不管理对话、不追踪 HR 回复（agent 看不到平台）
- 不判断薪资谈判、不准备面试题

## 4. 各 harness 的接入方式

### 4.1 按能力分档，不按产品分档

产品能力变化很快，按产品写适配会持续过期。毛遂按**四个能力维度**分三档：

| 维度 | 说明 |
|---|---|
| D1 | 能否自动发现技能（读 `SKILL.md`） |
| D2 | 能否读本地文件（简历、`.maosui/` 档案） |
| D3 | 能否执行代码（跑校验脚本） |
| D4 | 能否读图片（JD 以截图形式提交） |

| 档位 | 具备 | 使用方式 | 校验强度 |
|---|---|---|---|
| **A** | D1 D2 D3 D4 | clone 仓库，技能自动发现，一次配置长期可用 | 硬校验 |
| **B** | D1 D2 D4，无 D3 | 同 A，但校验降级为自检 | 软校验 |
| **C** | 仅 D4（或全无） | 手动粘贴：workflow 全文 + 简历文本 + JD 文本 | 软校验 |

档位 C 是底座。§1.3 的自包含原则保证了它一定能跑，只是每次要重新贴工作流。

### 4.2 各产品的档位归属

| harness | 档位 | 备注 |
|---|---|---|
| CLI 类 agent（Qoder、Claude Code 等） | **A** | D1–D4 齐备；D5（浏览器）也具备，是未来 Tier 1/2 的目标环境 `FACT` |
| ChatGPT | **B** | 自定义 GPT / Project 指令可承载 workflow，简历需上传而非读本地路径；代码执行环境能否跑本项目的校验脚本 `待验证` |
| DeepSeek 网页版 | **C** | 无技能发现与本地文件机制，走手动粘贴路径 |

`待验证`：上表第 2、3 行需在实现阶段用真实账号走一遍确认，产品能力更新频繁，本文档不保证时效。第 1 行由作者环境直接确认。

### 4.3 档位 C 的降级说明（要写进 README）

档位 C 使用者的每次使用流程：

1. 粘贴 `workflow/00-profile.md` 全文 + 自己的简历文本 → 得到档案，自己存到本地任意文件
2. 每次筛选时粘贴 `workflow/01-screen.md` 全文 + 档案 + 一批 JD 文本
3. 圈选后粘贴 `workflow/02-open.md` 全文 → 得到第二条消息
4. 自己去平台粘贴发送

**这是可用的，但明显更麻烦。** README 必须如实说明，不能只展示档位 A 的体验——否则档位 C 使用者会认为项目坏了。

### 4.4 JD 的提交形态

Tier 0 下 agent 不能打开链接，所以**贴链接是没用的**。可用形态：

| 形态 | 要求 | 适用 |
|---|---|---|
| 粘贴 JD 文本 | 无 | 全部档位，最稳 |
| 岗位页截图 | D4 | 省事，但依赖视觉识别准确性 |
| 岗位链接 | 需 Tier 1 | **v1 不支持** |

`待验证`（白皮书 §9.3 第 3 项）：作者实际用一段时间后确定推荐哪种。当前建议默认文本，截图作为省事选项。

## 5. v1 交付清单

可判定「做完了」的最小集合：

- [ ] `workflow/00-profile.md`、`01-screen.md`、`02-open.md` —— 各自满足 §1.3 自包含原则（判定方式：把文件内容原样贴进一个无上下文的对话模型，能产出符合 §3.3 / §3.4 格式的结果）
- [ ] `templates/profile.md` —— 含 §3.1 全部字段，含「明确不含」段落
- [ ] `platforms/platform-a.md` —— 会话机制与约束（招呼语全局固定、仅 APP 可编辑、可连发多条、纯文本要求）；页面动作序列留空并标注 Tier 1 起填写
- [ ] `skills/maosui/SKILL.md` —— 档位 A 入口
- [ ] `scripts/validate-message.py` —— 校验项：无 URL、无手机号、无 IM 账号、字数区间、不含招呼语原文
- [ ] `README.md` 补档位说明与 §4.3 降级流程
- [ ] 作者本人用它跑通至少一批真实岗位（5 个以上），并据此回填白皮书 §9.3 的第 2、3、7 项

最后一项是验收的核心：**毛遂的第 0 号用户是作者本人，没跑过真实求职的 v1 不算完成。**

## 6. 留给架构文档的问题

本文档不解决、需要 `architecture.md` 回答的：

1. `.maosui/` 的数据格式（Markdown 还是 JSON？人要不要能直接编辑？）
2. 适配层的接口形状——Tier 0 下它几乎没有内容，但接口要为 Tier 1/2 预留，怎么预留才不过度设计
3. 多平台并存时 workflow 如何引用适配层（现在只有一个，写死还是参数化）
4. `validate-message.py` 的校验规则如何与 `platforms/*.md` 里的平台约束保持单一来源，避免两处规则漂移
5. 技能入口在不同 harness 的格式差异（`SKILL.md` 是某一家的约定，不是通用标准）`待验证`
