# 毛遂 · 白皮书

> 版本：v0.2 · 2026-10-22
>
> v0.1 → v0.2 修订：定位收窄到「招呼语全局固定」这一实测平台缺陷；核心假设改写（原「精写第一句 > 群发」已因平台不可替换第一句而作废）；关闭两项反方论证（发送条数、内容审核），修正三处过强表述（Tier 0 下的节流硬编码、回复数可观测性、匹配失败即拒生成）；数据承诺由「留在本地」改为「不增加数据接收方」。
>
> 本文档中每个非平凡论断都带证据分级：
> - `FACT` — 可查证事实，或作者本人实测结果
> - `SIGNAL` — 有间接依据的推断，未严格验证
> - `HEURISTIC` — 设计判断，目前没有证据支撑，写出来是为了能被推翻
> - `待验证` — 需要查原文或实测，本文档不做猜测，见 §9.3 清单

## 0. 摘要

毛遂是一个开源的求职能力包，把「在招聘平台上开口」变成 agent 的一项技能。

它针对的是一个具体的平台缺陷：主流招聘平台的招呼语是**全局固定的一条**。你设置一次，之后每点开一个对话都自动发出同一句 `FACT`（作者实测，见 §1.1）。这句话对每个 HR 都一样，因此它携带的信息量是零——它没有证明你读过这份 JD，也没有证明你能胜任这个岗位。

毛遂不试图替换那句固定招呼语，因为平台不提供这个能力 `FACT`。它做的是：**在招呼语发出之后，生成第二条消息**。这一条引用这份 JD 里的具体要求，对应你简历里的真实经历，读起来像一个人写的，而不是一个模板填出来的。

三条硬承诺：**不碰账号凭据、不做托管服务、不做群发。**

第一版范围：单一招聘平台、社招场景、Tier 0（agent 不操作浏览器）、人在回路。

---

## 1. 问题：开口这一步被平台做废了

### 1.1 机制

在目标平台上，求职者侧的流程是：浏览岗位 → 点「立即沟通」→ 系统自动发出你预设的招呼语 → 进入对话。

作者实测确认的两点 `FACT`：

1. 招呼语是**全局设置**，不是按岗位设置。改一次，影响之后所有对话。
2. 招呼语配置**只能在移动 APP 端编辑**，网页端不可编辑。

这意味着一条理论上可行的人工路径：看到 JD → 打开 APP 改招呼语 → 回到网页 → 发起沟通。这条路存在，但每个岗位都要走一遍，实际操作中没有人会做。

**结论：在现有平台机制下，「针对具体 JD 定制第一句话」这件事对人类是不可行的。** 这不是懒惰问题，是交互设计问题。

### 1.2 求职者在这个缺陷面前的三种反应

| 反应 | 代价 |
|---|---|
| 海投，用数量对冲质量 | 账号风控风险；同时加剧 HR 侧噪音，让平台生态更差 |
| 逐个手写开场白 | 每个岗位 5–10 分钟读 JD 加想措辞 `HEURISTIC`，一天做不了几个 |
| 接受现状，发固定招呼语 | 开场白信息量为零，回复率取决于简历本身和运气 |

### 1.3 现有工具为什么没解决这个问题

- **平台自带推荐**：解决「看什么」，不解决「怎么说」。
- **群发/自动投递工具**：加剧 §1.2 第一行的问题，并且把账号置于风险中。
- **AI 改简历**：优化的是「我」，完全不读「岗位」。简历改得再好，发出去的开场白还是那一句固定的。

毛遂填补的正是这个空隙：**已经有一份好简历的人，缺的不是再改一次简历，而是让每一次开口都指向具体的岗位。**

### 1.4 切口

毛遂只做一件事：让开口的第二句话，带上这份 JD 和你这份简历的具体内容。

不追求覆盖求职全流程，不追求投递量，不做简历生成。

## 2. 为什么是现在

- agent harness（ChatGPT、Qoder、Claude Code、DeepSeek 等）已经普及，computer use / browser use 从演示变成日常可用工具 `FACT`。
- 求职者已经在大规模使用 AI，但用法几乎全部集中在「改简历」这一侧。「读岗位」这一侧基本是空白 `SIGNAL`。
- 关键变化：**现在每个求职者手边都有一个能读长文本、能做结构化对比的推理引擎。** 这在三年前不成立。毛遂不需要自己训模型，它只需要把工作流和平台适配层写清楚。

## 3. 给谁做

### 3.1 种子用户

**已经用 AI 改好简历、在招聘平台上主动沟通的社招求职者。**

三个特征缺一不可：

1. **在主动沟通，不是海投** —— 所以每个岗位都值得花力气定制。海投用户不是目标用户，毛遂的节流设计会主动把他们挡在外面。
2. **简历已经打磨过** —— v1 阶段毛遂只读简历，不生成简历。没有一份像样的简历，毛遂产出的第二条消息只会是把空话写得更长。（v2 的「定向简历」是在 §4.2 第 6 条边界内对已有内容做重排与强调，不是生成简历，与此不冲突。）
3. **能跑 agent harness** —— 这是真实门槛，本文档不粉饰。见 §3.3。

### 3.2 明确不服务的人

- 要托管代发的人：毛遂不碰凭据，没有服务端，做不到。
- 要提升投递量的人：毛遂的节流上限刻意设计为「一个人手动也能做到的量」，见 §7.4。
- 完全没有 agent 环境的人：Tier 0 降级路径要求用户能把 JD 贴给某个 AI 并把输出贴回平台。如果连这个都做不到，毛遂帮不上忙。

### 3.3 门槛的诚实说明

使用毛遂需要：一个能执行技能的 agent harness，以及把项目文件放进该 harness 可读位置的能力。对开发者这接近零成本；对非技术求职者这是硬门槛。

**白皮书不声称毛遂是普惠工具。** 第一版服务的是本来就在用 agent 的那批人。如果未来要扩大人群，需要的是一个封装好的应用，那是另一个项目，不在本文档范围内。

### 3.4 第 0 号用户

作者本人，正在用它找工作 `FACT`。这是开源项目里最强的可信度信号：毛遂的每一个设计决策都在真实求职中被使用，不好用的地方会立刻暴露。

## 4. 是什么，不是什么

### 4.1 四个动作与各自的成功标准

需求里原本只有动作定义，没有成功标准。没有成功标准就无法判断「做完了没」，因此本文档补上这一列。

| 动作 | 做什么 | 成功标准 |
|---|---|---|
| **提取** | 从已有简历读出结构化信息：技能、项目、偏好、硬性条件 | 关键项无遗漏；**且不新增任何简历里不存在的内容** |
| **操作** | 获取 JD 内容 | Tier 0：用户贴一次 JD 即可，无需二次追问。Tier 1+：用户不必手动复制 |
| **匹配** | 按 JD 给简历打分，说明为什么匹配、哪里不匹配 | 用户读完能自己判断「这岗值不值得开口」；**且不同意打分时能看出错在哪一步** |
| **开口** | 生成第二条消息 | HR 读完能确认「这个人读过我们的 JD」；文本中不出现可识别的模板痕迹 |

第三个动作的成功标准里「能看出错在哪」是刻意的：一个只给分数的匹配引擎不可信，也不可改进。**可解释性不是附加功能，是这个动作的定义的一部分。**

### 4.2 六件不做的事

1. **不碰凭据** —— 不存储、不代登录、不索取 cookie 或密码。
2. **不做托管服务** —— 没有毛遂的服务器，没有账号池，没有云端队列。
3. **不群发** —— 节流到人类节奏，默认逐条确认。
4. **不绕过验证码与风控** —— 遇到就停，交给用户。
5. **不代面试**。
6. **不伪造经历**。

第 6 条需要精确边界，因为路线图上的「定向简历」功能（§8）会直接压在这条线上：

> **只允许**：重排顺序、强调已有内容、按 JD 术语调整措辞。
> **不允许**：新增未发生的经历、改动任何数字（规模、性能、金额、人数）、调整时间线。

违反以上三条的「定制」就是伪造，毛遂不提供，也不提供绕过手段。

### 4.3 数据去向的诚实说明

原始需求里写的是「数据留在本地，不上传外传」。这句话按字面理解是不成立的，本文档改为可兑现的版本：

**毛遂自身不采集、不落库、不上报，不增加任何数据接收方。**

但必须说清楚：你的简历全文和 JD 内容会进入你所选择的 harness（ChatGPT / Qoder / DeepSeek 等），此后的处理由该 harness 的隐私政策约束。**任何跑在第三方模型上的方案都做不到「数据不出本地」**，声称做到的都是误导。

毛遂能承诺的边界是：它自己不成为一个额外的数据出口。本地缓存的简历结构化数据默认明文存储于用户目录，是否加密见 §7.3。

### 4.4 平台协议的立场

**用你自己的账号、在你自己的浏览器里、由 agent 操作，这件事仍可能违反平台用户协议。** `待验证`：需查目标平台协议原文，见 §9.3。

毛遂的态度是不假装这个风险不存在：

- 不声称「合规」，因为没有查证之前不能这么说。
- 不替用户承担风险，风险归属使用者本人。
- 不隐藏风险，README 与技能入口都必须显式提示。

项目提供的降险手段是：节流到人类节奏、逐条人工确认、不绕风控。这些降低概率，不构成免责。

## 5. 核心假设与观测方式

### 5.1 假设

> **「固定招呼语 + 定制第二条消息」的回复率 > 「只发固定招呼语」。**

分级：`HEURISTIC`。目前没有证据。

注意这个假设的形状**已经变过**。原始需求里的假设是「精写第一句 > 群发默认招呼」；由于平台不允许替换第一句（§1.1），该假设已作废，被上面这条替代。

### 5.2 反方论证

认真写，不是稻草人：

1. **HR 可能根本不读对话内容**，只看简历匹配度、期望薪资和在线状态。若如此，第二条消息的边际价值接近零。
2. **两条消息可能比一条更像机器人。** 一条通用招呼语后紧跟一条高度定制的消息，这个模式本身可能触发 HR 的「这是自动化的」判断。

这两条里第 1 条最难反驳，因为它无法从外部观测——你只能看到「没回复」，看不到「为什么没回复」。

**已关闭的反方论证**（保留记录，避免后来者重新提一遍）：

初稿曾列第三条「第二条消息可能压根发不出去」，含两个子风险，现均已关闭：

- *发送条数限制* —— 作者实测：HR 回复前可连发四五条，自动招呼语不计入其中，第二条消息不受限 `FACT`。
- *内容审核屏蔽* —— 用输出规范消除，而非查证：第二条消息强制纯文本，禁止手机号、微信/QQ、外部链接、附件与作品集指引（见 §6.5）。**注意这条风险是被规范消掉的，不是被平台证明不存在的**——所以该约束在实现层必须是硬校验，只写在文档里等于没写。

顺带澄清一个初稿写含糊的地方：毛遂经 browser use / computer use 在用户自己的浏览器里操作，产生的请求与用户手动操作在**传输层完全一致**，平台无法据此区分自动化与人工。所以「被识别为机器人而遭拦截」不是本项目的风险来源；真正需要担心的是产品规则和 HR 的主观判断，也就是上面剩下的这两条。

### 5.3 为什么这个假设很难被严格证明

单个求职者一轮求职的沟通量级是几十到几百次。要在统计上检出 10 个百分点的回复率差异，每组需要的样本量远超个人一次求职所能积累的量 `待验证`：需补功效计算。

更根本的问题是**选择偏差**：你只对自认为匹配的岗位开口，而「匹配度」同时影响回复率和「你是否愿意用毛遂」。这不是随机分组，前后对比里混着岗位质量的变化。

### 5.4 本项目采用的观测方式

**不做 A/B，不做跨用户聚合上报。** 只做一件事：毛遂在本地记录生成数，你自己看趋势。

这里有个 Tier 0 带来的限制必须写明：**agent 不接触平台，因此它看不到 HR 是否回复。** 回复数只能由用户回填，或等 Tier 1 之后由 agent 只读观测。所以 v1 能自动记录的只有「生成了多少条第二条消息」，回复率是需要用户自己填的空。这不是设计疏漏，是 Tier 0 的直接后果——初稿曾写成「记录发送数与回复数」，在 Tier 0 下不可实现，已更正。

这是弱证据，本文档明确承认。选择它的理由：

- 任何统计上更强的方案都需要跨用户聚合，而聚合需要一个服务端 —— 直接与「不做托管服务」（§4.2）冲突。
- 开源项目里的自愿上报有强幸存者偏差：愿意上报的通常是效果好的人。

`待裁决`：作者最初要求「白皮书要说明怎么验证」，本节是兑现该要求的最低成本版本。若认为这节多余，可整节删除；删除后 §5.1 的假设将以纯 `HEURISTIC` 形式留在文档里，不再声称任何观测计划。

### 5.5 如果假设被证伪，项目还剩什么

这一点必须在白皮书里回答，否则项目会因为一个实验结果而自我否定。

1. **省时间** —— 每个岗位的开口成本从数分钟降到数十秒。这个价值与回复率无关，独立成立。
2. **不越界** —— 用户不需要拿账号去赌群发。这个价值也独立成立。
3. **匹配打分本身有价值** —— 它回答的是「这岗值不值得开口」，这个判断的正确性可以独立于「开口效果」被检验。

**因此毛遂的定位立在两条腿上：(a) 不越界、可持续；(b) 定制更有效（待验证）。(a) 不依赖 (b)。**

## 6. 产品形态

### 6.1 能力包，不是应用

毛遂没有 UI，没有服务端，没有安装器。它是三层文件：

1. **通用工作流**（harness 无关）—— 用自然语言描述的步骤，任何能读文档的 agent 都能执行。
2. **平台适配层**（可扩展）—— 每个招聘平台一个适配文件，描述该平台的页面结构、动作序列、限制条件。
3. **技能定义** —— 把前两层包装成 harness 可识别的技能入口。

第一版只含一个平台适配层，但接口按可扩展设计，新增平台不需要改动通用工作流。

### 6.2 能力分级

| 级别 | 浏览器能力 | agent 做什么 | 平台风险 |
|---|---|---|---|
| **Tier 0** | 无 | 用户贴 JD 文本 → agent 出匹配 + 第二条消息 → 用户自己粘贴发送 | 零 |
| **Tier 1** | 只读 | agent 打开岗位链接读 JD，不发送任何内容 | 低（浏览频率是风控信号） |
| **Tier 2** | 可交互 | agent 填写聊天框，发送前强制人工确认 | 中 |

**v1 交付 Tier 0**，接口按 Tier 1/2 预留。

选择 Tier 0 的理由不只是风险低。见 §6.3。

### 6.3 Tier 0 的一个反直觉优点

如果 agent 自动发送第二条消息，它会在招呼语后 1–2 秒内到达。**这个时间间隔本身就是自动化特征**——人类读完 JD、想措辞、打字，需要几十秒到几分钟。

Tier 0 下用户手动复制粘贴，天然产生人类节奏的间隔。

也就是说：**「agent 不动浏览器」在这个场景里不是能力妥协，而是产物质量的一部分。** 这条会反过来约束 Tier 2 的设计——即便未来实现自动发送，也必须加入符合人类节奏的延迟，而不是尽快发出。

### 6.4 默认人在回路

生成队列 → 逐条确认 → 发送。全自动模式是显式开关，默认关闭，且开启时需要用户确认已理解 §4.4 的协议风险。

### 6.5 第二条消息的写作规范

这是毛遂的核心产物，规范必须写死而不是留给模型即兴发挥：

- **不重复**第一条招呼语的任何内容。第一条是废信息，第二条要承担全部说服任务。
- **具体**：必须引用 JD 里的某个具体要求或业务场景，并对应到简历里的某段真实经历。**找不到可锚定的对应点时，毛遂不编造一个**，而是告知用户「这岗找不到具体锚点」并给出匹配度判断，由用户决定要不要开口。（初稿写成「直接告诉用户这岗你不匹配」，过于绝对——七成匹配的岗位同样值得开口，拒绝生成会把这类岗位错杀。）
- **纯文本**：禁止手机号、微信/QQ 等联系方式、外部链接、附件与作品集指引。这既是 §5.2 关闭内容审核风险的前提，也让消息读起来不像推广。作品集留到 HR 回复之后再给。
- **不堆砌**：不用感叹号连击、不用「非常荣幸」「敬请垂询」类客套、不用 emoji。
- **降低回复成本**：结尾给一个 HR 容易回答的具体问题。`HEURISTIC`
- **长度上限**：`待验证` —— 需实测平台聊天框的折叠阈值。在查证前，采用 80–150 个汉字作为工作值 `HEURISTIC`。

`待裁决`：**第二条消息要不要提及第一条是自动发的？** 本文档推荐**不提及**——直接切入实质内容，读起来就像一个人打完招呼后开始正经说话，这是自然的人类行为；解释反而显得笨拙，并且会主动提醒 HR「这里有自动化」。此决定影响全部产出文本的语气，需要作者确认。

## 7. 风险

### 7.1 账号风险

自动化操作可能触发平台风控，导致限流或封号。缓解手段：节流到人类节奏、不绕验证码、Tier 0 下 agent 完全不接触平台。

Tier 0 的账号风险为零，因为 agent 不产生任何平台可见的行为。**这是 v1 只做 Tier 0 的最强理由。**

### 7.2 协议与法律风险

见 §4.4。`待验证`：平台用户协议原文。

### 7.3 隐私风险

简历含个人敏感信息（手机号、住址、身份证号等）。两个设计约束：

1. **提取动作必须做字段最小化** —— 结构化数据模型里不包含联系方式与证件号，因为开口和匹配都不需要它们。
2. **本地缓存默认明文** `HEURISTIC`。是否引入加密是 v1 的开放问题：加密会显著提高使用门槛（密钥管理），而威胁模型里「谁能读你的用户目录」在个人设备上通常不是一个现实威胁。本文档倾向不加密，但要在文档里写明缓存位置和删除方法。

### 7.4 伦理风险：把个性化开场白规模化，算不算更高级的骚扰？

这是本项目最需要正面回答的问题。分界线是：

> **毛遂的节流上限设计为「一个人手动操作也能做到的量」。**

如果某个用量人类手动做不到，那就是群发，不管文案多精致。

这条约束在不同 Tier 下落地方式不同，必须分开说——初稿写成「硬编码约束」，在 Tier 0 下是不成立的：

- **Tier 0**：agent 完全不接触平台，发送由用户手动完成。节流由人类操作成本天然约束。**没有任何硬编码限速能约束一个手动复制粘贴的人，也不需要。**
- **Tier 2**：agent 代为填写与发送，人类成本约束随之消失。此时节流上限必须是硬编码约束，且不可由用户配置放开。具体数值 `待验证`：需要作者用自己的真实求职节奏标定。

### 7.5 项目自身风险

平台页面改版会导致 Tier 1/2 的适配层集体失效。缓解：适配层与通用工作流解耦，失效只影响单个平台；Tier 0 不依赖页面结构，因此不受影响。**这是「v1 只做 Tier 0」的第二个理由——它对平台变更免疫。**
